Application Security - Enhancement Controls

Application Security - Enhancement Controls

APP-E-01

Control Name

소프트웨어 개발 수명주기 전 과정의 보안 통합·성과관리

Security Domain

Application Security

Control Class

Enhancement

Control Objective

애플리케이션의 요구사항 정의부터 설계, 개발, 시험, 배포, 운영·변경 및 폐기까지 소프트웨어 개발 수명주기(SDLC) 전 과정에 보안 활동을 통합하고 수행성과를 지속적으로 관리하여 개발 과정에서 발생할 수 있는 보안 위험을 예방하고 줄입니다.

Control Statement

개발 완료 후 취약점을 점검하는 방식만으로는 설계 단계의 결함이나 개발 과정에서 반복되는 보안 문제를 효과적으로 예방하기 어렵습니다. 따라서 조직은 보안을 별도의 사후 점검활동이 아니라 SDLC 전 과정에 포함되는 지속적인 활동으로 운영해야 합니다.

이 Control은 단계별 보안 요구사항과 검증 활동을 정의합니다. 보안검토율·시험 수행률·취약점 조치율과 같은 지표 및 정적 분석(SAST: 소스코드 분석)·동적 분석(DAST: 실행 중인 애플리케이션 분석)·소프트웨어 구성요소 분석(SCA: 외부 라이브러리 등의 취약점 확인) 결과를 지속적으로 추적하여 개발보안 활동의 효과성을 확인·개선하는 것이 목적입니다.

적용 조건

적용 시점

신규 애플리케이션 개발·도입, 중요 기능 변경, 시스템 개선·재개발, 운영 및 폐기 시 적용합니다.

적용 대상

자체개발 및 위탁개발 애플리케이션, 시스템 간 연동 인터페이스(API), 웹·모바일 서비스, 소프트웨어 구성요소와 개발·시험·배포·운영에 참여하는 조직·인력에 적용합니다. 개인정보처리시스템에는 관련 안전조치 의무를 반영하고, 일반 애플리케이션에는 조직의 개발보안 정책을 적용합니다. 적용 제외가 필요한 경우 범위·사유·위험·보완조치·승인자를 기록하되 법적 의무는 제외하지 않습니다.

관련 법령

  • 「개인정보 보호법」 제29조 — 개인정보의 분실·도난·유출·위조·변조·훼손을 방지하기 위한 기술적·관리적·물리적 안전조치 의무.
  • 「개인정보의 안전성 확보조치 기준」 제6조 — 개인정보처리시스템의 불법 접근을 제한하고 개인정보 유출 시도를 탐지·대응하는 등 접근통제 의무.
  • 「개인정보의 안전성 확보조치 기준」 제7조 — 인증정보와 법정 대상 개인정보의 저장·전송 시 암호화 및 해당 대상자의 암호키 관리 의무.

Control Owner

개발/애플리케이션 보안 책임자

Stakeholders

서비스 소유자, 정보보호 담당자, 개인정보보호 담당자, 품질보증(QA) 담당자, IT 운영 담당자, 구매 담당자·공급자

매핑된 ISMS-P 항목

  • 2.8.1 보안 요구사항 정의
  • 2.8.2 보안 요구사항 검토 및 시험
  • 2.8.3 시험과 운영 환경 분리
  • 2.8.4 시험 데이터 보안
  • 2.8.5 소스 프로그램 관리
  • 2.8.6 운영환경 이관

매핑된 CSF 항목

  • PR.PS-06 — Secure software development practices are integrated, and their performance is monitored throughout the software development life cycle.

Implementation Guide

1. 보안 개발 수명주기 기준 및 책임체계 수립

  • 요구사항, 설계, 개발, 시험, 배포, 운영·변경, 폐기 단계별로 수행해야 하는 보안 활동을 정의합니다.
  • 단계별 책임자, 수행자, 검토자 및 승인자를 지정합니다.
  • 자체개발뿐 아니라 위탁개발과 외부 소프트웨어 도입에도 적용할 기준을 정합니다.

2. 개발 초기 보안 요구사항 정의

  • 처리정보의 중요도와 개인정보 처리 여부를 확인합니다.
  • 인증·인가, 접근통제, 암호화, 세션관리, 입력값 검증, 로깅, 오류처리 등 필요한 보안 요구사항을 정의합니다.
  • 법적·계약상 요구사항과 조직의 보안정책을 개발 요구사항에 반영합니다.

3. 설계·개발 단계 보안활동 수행

  • 중요 애플리케이션은 필요한 경우 위협모델링 또는 이에 준하는 설계 보안검토를 수행합니다.
  • 안전한 코딩 기준과 코드리뷰 절차를 적용합니다.
  • SAST와 SCA 등 조직이 정한 자동·수동 검증수단을 개발 과정에 통합하고 발견된 문제를 추적합니다.

4. 시험 및 배포 전 보안검증

  • DAST, 취약점 진단, 보안 요구사항 시험 등 애플리케이션 특성과 위험에 적합한 검증을 수행합니다.
  • 발견된 취약점은 심각도와 조치 기한을 부여하여 추적합니다.
  • 배포 전 미조치 취약점과 잔여위험을 확인하고 정해진 승인기준에 따라 배포 여부를 결정합니다.

5. 운영·변경·폐기 단계 보안관리

  • 운영 중 발견된 취약점과 사고를 개발 프로세스로 환류하여 조치합니다.
  • 중요 변경사항은 최초 개발과 동일한 기준으로 보안영향을 검토하고 필요한 시험을 재수행합니다.
  • 애플리케이션 폐기 시 계정·권한, 데이터, 비밀정보, 저장소 및 관련 구성요소의 잔존 위험을 확인합니다.

6. SDLC 보안 성과 측정 및 지속적 개선

  • 보안검토율, 보안시험 수행률, 취약점 조치율, 미조치 취약점 수, 반복 취약점 등 성과지표·위험지표(KPI/KRI)를 정의합니다.
  • SAST·DAST·SCA 결과와 예외·미조치 항목을 지속적으로 추적합니다.
  • 지표, 사고, 취약점 및 예외 현황을 정기적으로 검토하고 필요한 경우 개발기준·도구·교육·절차를 개선합니다.
  • 개선 결과가 조직의 목표 보안수준(Target Profile) 달성에 기여하는지 확인합니다.

Evidence

  • 보안 개발 수명주기 정책·절차: SDLC 전 단계의 보안활동과 책임이 공식적으로 정의되어 있는지 확인합니다.
  • 보안 요구사항 정의서: 개발 초기부터 애플리케이션별 보안 요구사항을 식별·반영했는지 확인합니다.
  • 설계 보안검토·위협모델링 결과: 구현 이전에 주요 설계 위험을 검토했는지 확인합니다.
  • 코드리뷰 및 SAST 결과: 개발 단계에서 소스코드 보안문제를 식별·조치했는지 확인합니다.
  • SCA 결과 및 구성요소 관리기록: 오픈소스·외부 구성요소의 알려진 취약점과 위험을 확인했는지 검증합니다.
  • DAST·취약점 진단·보안시험 결과: 실행환경에서의 보안문제를 배포 전에 검증했는지 확인합니다.
  • 취약점 조치 및 예외 승인 기록: 발견된 문제의 조치 기한, 완료 여부 및 미조치 위험의 승인 여부를 확인합니다.
  • 배포·변경 승인 기록: 보안검증 결과가 실제 배포·변경 의사결정에 반영되었는지 확인합니다.
  • SDLC 보안 KPI/KRI 및 경영 검토자료: 개발보안 활동의 수행성과를 측정·검토하고 개선하는지 확인합니다.
  • 개선조치 이력: 반복되는 결함과 미흡 사항이 기준·도구·교육·절차 개선으로 이어졌는지 확인합니다.

ISMS-P Limitation

ISMS-P 2.8.1~2.8.6은 개발보안, 보안 요구사항, 구현·시험, 개발환경 및 변경관리 등 개발 과정의 주요 보호조치를 요구합니다. 다만 이러한 활동을 SDLC 전체의 하나의 연속적인 보안관리 체계로 통합하고, 단계별 보안활동의 수행률과 효과를 KPI/KRI 및 SAST·DAST·SCA 결과 등을 통해 지속적으로 측정·관리하며 개선하는 범위는 상대적으로 명시적이지 않습니다.

CSF Coverage

요구사항 정의부터 설계·개발·시험·배포·운영·변경·폐기까지 보안활동을 SDLC 전 과정에 통합하고, 보안검토율·시험률·취약점 조치율과 SAST·DAST·SCA 결과를 추적하여 개발보안 성과를 지속적으로 검토·개선함으로써 NIST CSF 2.0 PR.PS-06의 결과를 보완합니다.
